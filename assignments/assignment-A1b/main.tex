\section{Task 1: Solution Overview}

The Smart Turtle Breeding System (STBS) serves 20 indoor or semi-closed Chinese soft-shell turtle units. The architecture separates a device layer, a fog layer and a cloud layer. ESP32-C6 devices collect temperature, pH, ammonia, turbidity, level and flow data; local relay, PWM and driver outputs control the heater, valve and water-cycling pump. A Zigbee coordinator connects the wireless device links and food feeder to a Raspberry Pi 5 edge gateway. The IP camera uses Ethernet through the LAN switch, while the router provides the Internet gateway. The Raspberry Pi aggregates, filters and buffers local data, shows a local dashboard through HDMI, and uploads selected information to the IoT cloud platform over MQTT/HTTPS with TLS. Web, mobile and optional analytics applications support remote access, alerts and longer-term analysis \parencite{Prapti2022,Rastegari2023,Munyaev2026}.


\section{Task 2: IoT Devices}

\subsection{Overview and suitability}

The device set is chosen from the measurements the solution has to make, and it is split so that a fault on one path does not disable the other. ESP32-C6 \#1 handles water-environment sensing, while ESP32-C6 \#2 checks tank functionality and connects level and flow feedback to the water-change controls. GPIO/ADC, UART/I2C and Pulse/GPIO are used inside the device layer; Zigbee provides the short wireless links to the coordinator. The heater, valve and water-cycling pump remain under local relay, PWM or driver control. The IP camera uses Ethernet and the food feeder uses Zigbee. This arrangement keeps immediate control local while the Raspberry Pi 5 gateway aggregates, filters and buffers data before cloud upload.

\section{Task 3: IoT Network Technology}

The device layer is wired by interface requirement rather than by convenience: 1-Wire/GPIO for temperature, RS-485 Modbus through an isolated RS-485-to-UART converter for the combined pH/NH\textsubscript{3}-N sensor, GPIO/ADC for the analog turbidity and pressure-derived level sensors, Pulse/GPIO for flow, and relay/PWM/driver outputs for the heater, normally-closed valve and AC electric water-cycling pump \parencite{EspressifESP32C6DevKitC1,DFRobotDFR0845}.

The link between the devices and the network devices is then chosen on range, data rate, latency and power consumption, not on preference for one radio \parencite{Rayes2022}. Each tank is at most about 30\,m by cable route from the coordinator and the whole farm is inside one building, while the aggregated telemetry for all 20 tanks is about 2.4\,kbps, so the scenario needs neither long range nor high rate. Zigbee under IEEE 802.15.4 (10--100\,m, below 250\,kbps, 20--50\,ms, very low power) and Wi-Fi (50--100\,m, above 100\,Mbps, below 10\,ms, high power) both cover the distance and both exceed the payload by two orders of magnitude, so range and rate do not separate them. Zigbee is selected because power and spectrum do: its very low power draw lets the radio run from the same 3.3\,V rail as the ESP32-C6, and 802.15.4 channels 15, 20 and 25 fall in the gaps between Wi-Fi channels 1, 6 and 11, so the farm Wi-Fi and the device links coexist without contention. Wi-Fi would buy 100\,Mbps that 2.4\,kbps of telemetry cannot use, in exchange for a DHCP association and a higher idle current at each of the 20 nodes. Ethernet (100\,m per segment, above 1\,Gbps, below 1\,ms) is rejected for the sensor nodes because cabling 20 tanks is not justified by the payload, but it is kept for the camera, whose 4--8\,Mbps at 8\,MP and 25\,fps is one to two orders of magnitude above the Zigbee ceiling, and for the fog backbone; MQTT/HTTPS over TLS then carries the selected data from the gateway to the cloud. Latency does not discriminate at this scale, because heater, valve and pump decisions are taken by local relay, PWM and driver outputs and never wait for a wireless round trip, so the 20--50\,ms Zigbee latency only affects dashboard refresh. 4G is retained as an uplink fallback for the gateway rather than as a device link.

\section{Task 4: Fog and Cloud Computing}

The Raspberry Pi 5 is the fog gateway for data aggregation, local control rules, filtering, optional video processing, local buffering and upload to the cloud. The USB Zigbee coordinator bridges the ESP32-C6 and Aqara feeder links to the gateway. The HDMI-connected local monitor is display-only. The router provides the Internet gateway, while the IoT cloud platform supports long-term storage, analytics, notifications, remote access, model training and device management. The cloud is therefore useful for applications and historical analysis but is not placed in the immediate actuator control loop \parencite{RaspberryPi5,SONOFFZBDongleE}.

\subsection{Description of the diagram}

Figure~\ref{fig:architecture} follows the three-layer structure and connection legend: the device layer senses and actuates, the fog layer aggregates, filters and buffers local data, and the cloud layer stores, analyses and presents authorised results. ESP32-C6 \#1 and \#2 implement the two local device functions, with 1-Wire/GPIO, RS-485/UART, GPIO/ADC and Pulse/GPIO connections to the sensors and relay/PWM/driver outputs to the heater, valve and AC electric pump. The Aqara food feeder is a native Zigbee device; the IP camera uses Ethernet RJ45. The Raspberry Pi 5, USB Zigbee coordinator, switch and router provide the fog/network path, while MQTT/HTTPS over TLS carries selected data to the cloud. Immediate control remains local and does not depend on a cloud round trip.

\section{Task 6: Conclusion}

The design links continuous water and feed measurements, bounded actuation, video evidence and role-specific alerts across 20 units. Immediate sensing and actuation stay in the device layer, Zigbee and Ethernet connect the local system, and aggregation, filtering and buffering are assigned to the Raspberry Pi 5 fog gateway. The water-cycling pump is an AC electric actuator, while the food feeder is a native Zigbee device. The cloud adds long-term storage, visualisation, alerts, remote access and optional behaviour or nesting analytics. The main limitations are probe fouling and calibration effort, Zigbee range and 2.4\,GHz contention over the 30\,m worst-case links, dependence on local gateway and switch power, and the need to validate video models under changing light, water and turtle density. Ammonia and video inference are indicators rather than diagnoses, while feeder runtime only estimates delivered mass. A staged pilot should validate thresholds, wireless coverage, hydraulic timings, electrical protection, false-alarm rates, model performance and operating procedures before all 20 units are commissioned.
